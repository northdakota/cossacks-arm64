# Known issues, fixes and workarounds

A running log, kept up to date with every change: what we found and fixed, and every shortcut
("workaround") that still has to be done properly. Before a release, the **Open** and
**Workarounds** sections become the release's list of known limitations; what else the release
notes must say (recommended settings) is in `release-notes.md`.

Each entry: what the game does, what the host does about it, and the evidence (an address in
`dmcr.exe`, GOG build `b4eea674…`, or a file). Statuses: **fixed** (done properly), **workaround**
(works, but not the real behaviour; revisit), **open** (not done).

## Open

| Issue | Notes |
|---|---|
| No intro or briefing videos | MCI `AVIVideo` is refused (`winmm.cpp`). The videos are Cinepak 640×360/480 with PCM or MS-ADPCM sound; FFmpeg decodes both. The engine opens them at 0x4c68fc (`MCI_OPEN` with `MCI_OPEN_TYPE|MCI_OPEN_ELEMENT`), then `MCI_WINDOW` 0x841, `MCI_PUT` 0x842, `MCI_PLAY` with notify. |
| No multiplayer | Winsock 2 refuses to start (`WSAStartup` → `WSASYSNOTREADY`), `CoCreateInstance(CLSID_DirectPlay)` → `REGDB_E_CLASSNOTREG`, `DirectPlayLobbyCreateA` → `E_FAIL`, the 10 functions of GSC's `iChat.dll` do nothing (`system.cpp`). |
| Historical battles and user missions not checked | The mission DLLs are placed in memory (fixed, below), but only the tutorial and a single mission were played. The historical battles (`History_battl`, 19 DLLs) were not found in the menus of *Back to War*; a mission DLL made by the player in the write folder is not placed (only the game folder's). |
| No report when the host itself crashes | The crash report (below) covers the program stopping on an error the host detects. A crash of the host (a signal such as SIGSEGV in native code) still ends without a report. |
| The app is not notarized, and Apple Silicon only | `tools/make_app.py` signs it ad hoc: macOS refuses to open a downloaded copy until the player allows it (Privacy & Security, or `xattr -dr com.apple.quarantine`). No Intel build yet. The app looks for a GOG copy only in CrossOver bottles (GOG Galaxy's folders, `dmcr.exe` of the GOG size), else asks for the folder; it cannot unpack a GOG installer itself (zeus-poseidon-arm64 carries innoextract for that). |
| In-game help does not open | The engine starts `HView.exe` with `WinExec` (0x4a08a6): refused, the host starts no other program. |
| Game speed follows the frame rate | The engine's simulation is tied to its frames: one step per frame, the AI playing once every 8 frames. The Options screen's Game Speed is a frame limiter: at the end of each frame (0x4d1ab2) the engine waits until 2 × `[0x718410]` ms have passed since the previous one (the slider shows 100 − that value; mode.dat's 7th number; 50 by default = 100 ms = 10 frames a second, 17 = 34 ms = 29, 8 = 16 ms = 62.5, 6 = 12 ms = 83). Game Mode (mode.dat's 9th number, `[0x5e4dec]`) sets how far things move in one step: Fast = 2 (`[0x5e4de4]`, used by the movement code, 0x52xxxx), Slow = 1. So for a given pace of play, Slow mode with a high frame limit gives twice the frames of Fast mode: the user found that Slow mode with the slider near the maximum plays at a comfortable pace and scrolls smoothly (2026-11-14). Where the emulation cannot reach the limit, the game runs slower than asked. Measured 2026-11-14 at 1664 × 1080, scrolling with the arrows, headless: 45–63 frames a second at 8, a steady 29–30 at 17. Short stretches at 6–20 frames a second (emulation 98 %) remain in some scenes, the start of a battle among them. If needed later: while paused the engine draws and scrolls the map without stepping the simulation (0x4ce92e, from the same wait loop when `[0x8fbb1c]` is set; checked); drawing such frames during the wait would decouple scrolling from the game speed entirely. Not done. |
| Performance: a battle is bound by the emulation | At 1664 × 1080 a battle runs at 31–51 frames a second on the real screen with one core at about 95 % (62 headless at the start of a battle). The engine is single-threaded and runs in one emulated CPU. Profile, native replacements so far (screen copy, the three sprite blitters) and the placement of the translated code: `docs/profiling.md`. **Plan:** profile a busy battle (`--profile` per block, `tools/profile_report.py` from upstream; `COSSACKS_PACE=1` for the frame figures), name the hot functions among the 552 exports and the code around them, then replace them natively one by one as in zeus-poseidon-arm64 (sprite blitters at 0x47b491 and siblings, the LZ decoder at 0x485070, terrain drawing, path finding), each checked against the original (`--no-native`, frame and state logs). Native replacements can use several cores or the GPU where it pays (see the notes in the README). |
| Only one build of the game tested | GOG *Back to War* 2.1.0.18, `dmcr.exe` SHA-256 `b4eea674…`. *European Wars* and *The Art of War* installers not analysed. |
| Other language editions not tested | Only the English GOG build is tested. To test before a release (asked by the user 2026-11-14): the Steam edition's Russian, German and French depots (app 4850, depots 4852–4855), Russian retail discs, fan translations. What may break: a different `dmcr.exe` build (the native replacements check their bytes and step back, but the host's own hooks are at fixed addresses: frame ends 0x4720d7, 0x4c5a0b, 0x45fb27, the arrow poll 0x4ed81b); Cyrillic text in names and chat (`ToAscii` knows a US layout only, file names and the code page 1251); fonts. The engine reads loose files before `ALL.GSC` (`gOpenFile`, `FindFirstFileA` at 0x402df8), so a translation can sit beside the game without changing it. Checked 2026-11-14: the Steam edition's Russian data (its `all.gsc`, `patch01.gs1` and a few texts and pictures; its own `dmcr.exe` is another build, 2 016 008 bytes, and is not used) as a language pack over the GOG engine (`--language DIR`, with `codage.txt` = 1251): menus, mission descriptions and the battle interface show in Russian. Cyrillic typing (through the code page 1251) not checked. The pack is for testing only and is never part of a release. The Steam edition's own `dmcr.exe` (SHA-256 `3923b0ff…`, 1.35 built in 2011) also runs, from the Steam folder, read only (2026-11-14): menus and a battle against three AIs, headless. It imports DirectDraw and the mci, mmio and mixer functions from `CSEMU.DLL` (served by the host like `MDRAW.DLL` and `MINMM.DLL`) and two set-up functions of `BUGTRAP.DLL` (without effect), and copies the screen with SSE. What the host ties to the GOG build is off there, its bytes not matching: W A S D, P and delete, the frame pacing (the periodic refresh shows the screen), the native replacements. Porting them means finding the same code in that build. |

## Workarounds (revisit before calling them done)

| Area | What the host does | Why it is a workaround | File |
|---|---|---|---|
| Screen refresh | The engine writes straight into the primary surface (it locks it twice in a session; on Windows that memory is the screen, and GSC's `mdraw.dll` presents it from a thread). The host marks a frame finished after the engine's copies to the primary surface (whole screen in `DialogsSystem::RefreshView`, call at 0x4720d2; changed rectangles, 0x4c5a06; end of `FlipPages`, 0x45fb27) and shows it once, when the engine starts waiting for its next frame (second `GetTickCount` in a row), or, when the engine finishes its next frame without having waited (it is behind), at that moment. A periodic refresh every 100 ms covers anything else (the cursor drawn straight on the screen, screens without those copies). | The frame end is found by hooks at fixed addresses of this build (bytes checked) and by the engine's clock loop, not by a documented signal. Measured headless in a battle: 29.5 presents/s for 28 new frames/s (5 % duplicates, was 53 %), gaps mostly 25–40 ms. The engine itself draws about 30 frames/s in battle (tied to the game speed). | `ddraw.cpp`, `process.h`, `kernel32.cpp`, `cossacks_run/main.cpp` |
| Busy clock | After 64 `GetTickCount` calls from one call site, with no other system call and less than 5 µs of the program's own work in between, each further call sleeps 1 ms. | The engine may wait by reading the clock in a loop. The sleep is not in the original; it may round frame times up by up to 1 ms. Reads around work (the path finding of each unit is timed, 0x53c1b2) must not count as a wait: see the fix of 2026-11-25. | `kernel32.cpp` |
| Idle message loop | An empty `PeekMessageA` returns at most every 4 ms, except for a game whose frames the host knows (Cossacks), where it returns at once (`COSSACKS_PEEK_IDLE=1` brings the wait back, for comparison). | Cossacks paces itself with its clock; the wait cost it half its frames (it calls `PeekMessageA` about 200 times a second). In return the menus spin freely: over 400 frames a second, one core busy (presents are capped at 120 a second). A limiter at the engine's clock wait was tried and dropped: the second clock read in a row happens several times per frame in a battle, and the battle fell to 12 frames a second. | `user32.cpp`, `process.cpp` |
| Missing CD tracks | A CD track with no `Tracks\Track_NN.ogg` (Back to War's new nations ask for 20 and later; GOG ships 2–19) plays an existing track instead. | GOG's own `minmm.dll` plays nothing then. An improvement on GOG, but not the original behaviour; the choice of replacement is arbitrary (`(N − 2) mod count`). | `winmm.cpp` |
| MCI notifications | Only `MCI_NOTIFY_SUCCESSFUL` at the natural end of a track; a stop or a new `PLAY` drops the pending notification silently. | Windows sends `MCI_NOTIFY_ABORTED` / `SUPERSEDED`. The engine's handler (0x574720) only acts on `SUCCESSFUL`, so this is enough for it. `MCI_STATUS` is not written. | `winmm.cpp` |
| DirectSound buffers | A buffer is turned into a sound at `Play`, cached until the next `Unlock`; `GetCurrentPosition` is estimated from the mixer; no 3D sound (`QueryInterface` → `E_NOINTERFACE`). | A buffer written while it plays (streaming) would not be heard changing. The engine's effects are static buffers, so it works for them. | `dsound.cpp` |
| W A S D | W A S D are the arrows while the engine polls the arrows to scroll the map (`GetKeyState(VK_RIGHT)` at 0x4ed81b, run every frame on the battle map and skipped while a text is typed); with Ctrl or Alt held they stay letters. The code bytes there are checked first. | A sign taken from the engine's timing (polled less than 250 ms ago) rather than a state variable; the flags it tests before polling (0x5e4df0, 0x8fbb55, 0x1026234) are not named yet. W A S D shortcuts of the engine, if any, are lost on the map. `COSSACKS_KEYLOG=1` logs every key. | `desktop.cpp`, `cossacks_run/main.cpp` |
| Wide screen | `EnumDisplayModes` offers, besides the usual 4:3 modes, modes in the proportions of the Mac's screen (heights 720–1080, widths a multiple of 32). | Not checked yet that every screen of the engine (menus, minimap, briefing) lays out well at those sizes. | `ddraw.cpp` |
| Pacing figures | ⌘I shows an overlay over the picture, refreshed every second: the engine's frames per second, presents per second and what triggered them (the engine's wait, a frame finished without a wait, the 100 ms timer), present time (average, longest, longest wait for the screen in `SDL_RenderPresent`), the longest gap between presents, and the share of time in emulation, presenting and idle. `COSSACKS_OVERLAY=1` turns it on from the start, `COSSACKS_PACE=1` writes the same figures to the error output. | A diagnostic tool, not a feature; its 5 × 7 font knows capitals, digits and a few signs only. | `desktop.cpp`, `process.cpp` |
| P = pause | On the map (same sign as W A S D) P is sent as Pause (`VK_PAUSE`), the engine's pause key in this build (checked: the game clock stops; P itself does nothing there). | A Mac keyboard has no Pause key. If P has another use on the map, it is lost. | `desktop.cpp` |
| delete = Delete | On the map (same sign as W A S D, so not while a text is typed) the Mac's delete key, Backspace, is sent as Delete (`VK_DELETE`), the engine's key to blow up the selected buildings and kill the selected units (checked: the selected units die; in the chat, "abc" and delete give "ab"). The forward delete (fn + delete) is Delete everywhere. | If Backspace has another use on the map, it is lost. | `desktop.cpp` |
| Keyboard to text | `ToAscii` knows a US layout only. | Other layouts give wrong characters for signs. | `user32.cpp` |
| File times | Local time is UTC (`FileTimeToLocalFileTime` and the reverse are the identity). | Saved-game times may show off by the time zone. | `system.cpp` |
| Registry | Kept in `registry.txt` in the write folder. | Only the five functions the engine uses; no enumeration, no deletion. | `system.cpp` |
| Files opened for writing | A file of the installation opened with `GENERIC_WRITE` is first copied into the write folder (VFS rule), even if the engine never writes it. | The engine opens every clan picture (`Clans\*\*.bmp`) read-write six times: about 200 copies on the first run. Harmless, but a lazy copy (at the first write) would be cleaner. | `kernel32_files.cpp`, `vfs.cpp` |
| File mappings | `MapViewOfFile` places the file itself in the emulated memory (`mmap`, copy-on-write) from 0x40000000 up. | Views never reuse their addresses (2 GB in all); only `PAGE_READONLY` and `PAGE_WRITECOPY`; a mapping larger than its file is refused. | `kernel32_files.cpp`, `cpu.cpp` |
| DLL loading | Every DLL the engine may load is placed in memory before the start; `LoadLibraryA` restores its bytes as loaded and calls `DllMain`. | Memory the DLL's C runtime allocated is not reclaimed at `FreeLibrary` if the DLL does not free it. The DLL area is 256 MB (0x20000000–0x30000000). | `modules.cpp`, `process.cpp` |
| C runtime of `AI\Denmark.dll` | `msvcrt.dll`: only `malloc`, `free`, `sprintf`, `_initterm`, `_adjust_fdiv` (0). | Enough for this one module. | `system.cpp` |
| Mixer | One device: the speakers (destination) with two sources, CD (the music's volume, 0x1005) and wave (0x1008), each with one volume control. Only the CD volume acts (on the music's voice); the speakers' and the wave's are kept and returned, without effect. The volumes are kept in the write folder (`mixer.txt`), as Windows keeps them, and in whole hundredths, each stored as the smallest value that reads back as the same hundredth. | The engine sets the music volume through the CD line about every frame on the Options screen (0x576101) and reads it back when the screen opens (0x5748b9: × 100 / 65536, then × 65535 / 100 when written): with the exact value, every visit lowered the music by 1 %. A real driver's steps may differ. Whether the engine also uses the wave line for "Sound Volume" is not checked (that volume is in mode.dat). | `winmm.cpp` |
| Exceptions | `RaiseException` stops the program with its code; `RtlUnwind` is not written. | C++ exceptions and SEH of the engine are not supported; none seen so far. | `system.cpp` |
| Locale | `GetLocaleInfoA` answers only the code pages; `GetLocaleInfoW` nothing. | Enough for the C runtime's start. | `system.cpp` |
| Heap | One 256 MB heap (0x10000000), an allocator of the host's own: best fit among free blocks, split to the size asked, freed blocks merged with their free neighbours and given back to the end; `HeapReAlloc` grows or shrinks in place when it can. `HeapCreate` heaps are the same heap. | Not Windows' allocator: a program that relied on its exact addresses or reuse order would differ (none seen: 5956 frames identical with both allocators). A battle levels off at about 35 MB handed out (`COSSACKS_HEAP_STATS=1` prints it every minute); 256 MB is still a hard limit. | `process.cpp`, `kernel32_memory.cpp` |
